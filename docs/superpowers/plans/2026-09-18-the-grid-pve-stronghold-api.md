# Grid PvE Stronghold Player API

## Goal

Expose the completed PvE stronghold stack to authenticated players without leaking internal database identity or trusting client combat state.

## Endpoints

- `GET /api/grid/strongholds`: authenticated/private stronghold list. Uses registry + runtime-evidence readiness. Returns a generic `503` when enabled definitions cannot be projected authoritatively; exact missing facts remain server-side.
- `POST /api/grid/strongholds/[strongholdId]/contest`: authenticated contest start. Client supplies only source territory slug, attacker commitment, and idempotency key.
- `POST /api/grid/stronghold-contests/[contestId]/round`: authenticated round command. Client supplies only idempotency key; all dice are generated by `cryptoSignalDiceRoller` on the server.

## Privacy and authority

The API accepts territory slugs rather than database UUIDs. Start and round responses are sanitized and do not return city/season/player/source/target internal IDs or event IDs. Stronghold faction/garrison/objective state comes from the trusted registry/readiness resolver. Missing strategic evidence blocks the start rather than defaulting to weaker values.

Both write endpoints reuse the existing `GRID_CONTEST_WRITE_ENABLED` gate and the real Founding Season contest configuration. The read endpoint uses `GRID_WORLD_READ_ENABLED` and requires authentication.

This checkpoint intentionally does not edit the already-claimed `/api/grid/world` or City Board UI. Those surfaces can consume these endpoints after canonical integration merges the NPC branch.
